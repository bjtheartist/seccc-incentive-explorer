# Audit — PR #247 "R2 data-integrity round"

**Verdict: NEEDS-FOLLOWUP** — the hardening is real and the request-validation/cache traces hold up, but three of the PR's headline claims ship plumbing with no consumer, and one whole subsystem (`lib/env.ts`) is never imported.

## Findings

### High
1. **CONFIRMED — `lib/env.ts:243` — the env doctrine never runs.** The module self-executes `assertEnvOnce()` on import, but nothing in `app/`, `lib/`, `components/`, `next.config.ts` or an instrumentation hook imports it; the only importer is `lib/__tests__/env.test.ts`. Failure: set `DOCUMENTS_ENABLED=1` in prod → the flag still silently reads OFF, nothing logged — exactly the defect the file was written for. Fix: import it from `instrumentation.ts` (`register()`) or `lib/db.ts`, and add a test asserting a real importer exists.

### Medium
2. **CONFIRMED — `lib/permit-exhibit.ts:1273` — `truncation` is computed but never rendered.** Zero references to `truncation` in `app/permit-exhibit/**`, `app/print/permit-exhibit/**`, `components/permit-exhibit/**`. Its own doc says "every surface rendering it must say so." Failure: a dense downtown PIN at 1000 ft hits the 20,000-row cap → the exhibit renders with the same header, counts and methods footer as a complete one, and the reader is told nothing. The new `request-bounds.test.ts` only greps `permit-exhibit.ts` for literal strings and type-checks the interface — it never builds a truncated exhibit or asserts a rendered notice. Fix: render `meta.truncation.notice` in `MethodsFooter`/`PermitExhibitHeader` and test it.
3. **CONFIRMED — `lib/fetch-cache.ts:117` — `cachedFetchWithMeta` has zero production callers.** Every existing call site still uses `cachedFetch`, which throws the flag away (`:181`). The stated defect ("no surface could have disclosed the difference") is unchanged in the shipped UI; only the capability exists. Same pattern as `parcel.checkedAt`, which the PR *does* disclose as unconsumed — this one it does not.
4. **PLAUSIBLE — `lib/schemas.ts:178` — `safeParseArray` now drops live DB rows.** Callers include DB paths, not just static files: `lib/data.ts:62,80`, `app/api/programs/route.ts:101` (`programs-api`), `app/api/stacking/route.ts:82`. Failure: a `programs` row whose `level`/`status` drifts outside `ProgramSchema`'s enum, or a null `summary`, previously rendered (raw passthrough) and now silently disappears from `/api/programs`, `/api/stacking` and every generated report, with one `console.warn`. Tests only exercise synthetic fixtures; nothing pins the production DB row shape against `ProgramSchema`. Fix: add a test (or a startup check) validating the actual `programs`/`stacking_rules` table shape before relying on drop semantics.
5. **PLAUSIBLE — `app/api/parcel/route.ts:362,514` — TTL 30d→24h *and* 4→6 decimal keys, compounded.** 6 decimals ≈ 0.1 m, so coordinate lookups (map clicks, drawn-area sweeps) are now effectively never cache hits, not just "less collided". Combined with the 24h TTL this multiplies live CookViewer + Assessor traffic on the app's busiest lookup path, and each miss now also holds a function slot for up to the new `maxDuration = 30`. The PR argues correctness (correct) but never bounds the cost. A middle precision (e.g. 5 decimals ≈ 1 m) would fix the collision without discarding the bucket.

### Low
6. **CONFIRMED — `app/api/report/generate/route.ts:88` — byte cap measured in UTF-16 code units.** `rawBody.length > MAX_GENERATE_BODY_BYTES` with no `Content-Length` header lets a body of ~4 MB of 4-byte characters pass a 1,000,000-*byte* ceiling. Fix: `Buffer.byteLength(rawBody, "utf8")`.
7. **CONFIRMED — `app/api/email-report/route.ts:125` — still trusts the declared `content-length` only.** The sibling route was fixed in this same PR precisely because "an oversized or lying Content-Length" must be refused either way; email-report was left with the declared check alone (the zod `.max()` after `request.json()` is the only real backstop).
8. **CONFIRMED — `app/api/report/generate/route.ts:109` — the limiter is consulted after validation.** A scripted caller sending bodies that fail zod hammers the route at any rate and never increments the counter. Cheap per request, but the limiter bounds *successful generations*, not request volume — worth saying so in the module doc, which currently claims it caps "a scripted caller at 120 engine runs an hour".
9. **PLAUSIBLE — `lib/report-generate-rate-limit.ts`** — identifier is the first `x-forwarded-for` hop, so a client that sets its own header rotates buckets freely; and the new table is indexed on `created_at` only while the hot query filters `client_hash = $1 AND created_at >= now() - 1h`. Both mirror the pre-existing email limiter, so this is consistency rather than a new defect.
10. **PLAUSIBLE — `lib/report-email.ts:147`** — `AbortSignal.timeout()` is called unguarded; on a browser without it (Safari < 16) this throws a `TypeError` before the request, converting a hang into an unexplained failure.

## Claims vs. diff
- **"Env doctrine"** — `lib/env.ts` exists and is well documented, but is unreferenced; no boot-time validation occurs in any environment. (#1)
- **"Cache honesty"** — half-delivered: `cachedFetchWithMeta` (#3) and `parcel.checkedAt` both land with no consumer. The `checkedAt` half is disclosed in the PR body; the `cachedFetchWithMeta` half is presented as a fix.
- **"permit queries LIMIT 20,000 with truncation marker"** — the marker is produced but not shown to any reader. (#2)
- **"File tracing"** — verified: every *live* `data/private` / `data/curated` request-time reader is now traced, and `loadCapitalContextForArea`'s only two callers (`/api/report/generate`, `/print/investment/[area]`) are both declared. Two more readers of those trees are undeclared — `lib/tif-briefs.ts` → `data/private/tif-briefs.json` and `lib/corporate-direct.ts` → `data/curated/investment-inputs/` — currently harmless only because neither has a production caller, and the new test's "no blanket tree glob" rule will not catch them when one is wired up.
- Verified as delivered: zod v4 API usage is correct (`.passthrough()`, `.finite()`, `z.record(k,v)`, `z.enum(..., {message})` all behave as the tests assume, checked against installed zod 4.3.6); `lib/redis.ts:43` already accepts a TTL *function*, so the `mismatch → 0` opt-out works end to end and is not test-only fiction; the real client payload in `app/report/page.tsx:1302,1780` uses `?? undefined` throughout, so the non-nullable `ctx` members in `ReportContextRequestSchema` do not break it.

## Scope creep
- `lib/env.ts` — 245 lines and a new subsystem for a finding that ends up only documented, not enforced.
- `app/investment/gate.tsx` — `InvestmentLoginForm` converted from a sync component to an **async server component** plus a `react.cache()` probe. Structural, and outside the "data integrity" theme. Verified safe: all four callers (`app/investment/page.tsx:44`, `[area]/page.tsx:171`, `compare/page.tsx:67`, `print/investment/[area]/page.tsx:135`) render it as JSX from server components.
- Test style: `request-bounds.test.ts` and parts of `data-private-curated-bundling.test.ts` assert on **source text** (`expect(source).toContain('subjectTruncated && areaTruncated ? "both" : …')`). These pin formatting, not behavior — they pass whether or not the truncation marker is ever emitted or displayed.

# Review — PR #248 (R1 user-facing correctness)

**Verdict: NEEDS-FOLLOWUP** — the honest-copy work is sound, but 2 of the 3 full-page retry buttons are no-ops and the client fetch layer silently defeats the new geocode 503.

## Findings

### High — 2 of 3 retry buttons never re-run anything (CONFIRMED)
`app/report/page.tsx:1946-1952`. `retry()` does `setCorridorAutoGenerated(false)` / `setShareAutoGenerated(false)`, but both flags are set to `true` **only on success** (`:1376`, `:1466`) and are already `false` after a failure. Setting state to its current value is a no-op, and neither effect's dep array (`:1359`, `:1421` gates) contains `reportError`, so the effect never re-runs.
Scenario: `/report?corridor=60636&preview=corridor-poc`, `/api/report/generate` 500s → honest card renders → click "Try again" → no POST is issued; the card disappears and the reader is dumped into the blank wizard (`report` is null and the loading gate at `:1992` requires `corridorLoading || isGenerating`, both false). Same for a shared link.
Fix: add `const [retryNonce, setRetryNonce] = useState(0)`, include it in the corridor/share effect deps, and have `retry()` bump it.

### High — `cachedFetch` stale-while-error swallows the new geocode 503 (CONFIRMED)
`lib/fetch-cache.ts:147-152` returns `{data: existing.data, stale: true}` on a non-2xx when the same URL has a prior cached success, and `cachedFetch` (`:180`) throws `stale` away. `handleGeocode` (`app/report/page.tsx:1580-1586`) uses `cachedFetch`, so once an address has geocoded successfully, a later `/api/geocode` 503 returns the **old coordinates as if fresh** — `geocodeFailureMessage` never runs and the report is built on stale data. This is precisely the "stale rendered as fresh" class the PR claims to close, at the layer the PR didn't touch.
Fix: use `cachedFetchWithMeta` at the geocode call site and treat `stale: true` as an outage, or bypass the client cache for geocode.

### Medium — a mobility outage is frozen into a 24h cache (CONFIRMED)
`lib/mobility-access.ts:703` wraps the whole result — including `unavailableSources` and the degraded "Transit data temporarily unavailable" labels — in `memCached(..., MOBILITY_CACHE_TTL_SECONDS = 86400)`. One transient CTA/Socrata 5xx pins the unavailability copy for 24h for that coordinate, for every reader, long after the feed recovers. The PR applies the opposite (correct) discipline two files over in `lib/zoning-point-lookup.ts:66-78` ("must NOT be stored… would freeze a transient outage").
Fix: throw (or cache with a short TTL) when `unavailableSources.length > 0`.

### Medium — `MajorDevelopments` unavailable branch is unreachable in production (CONFIRMED)
`components/investment/MajorDevelopments.tsx:33-44` is only reached via `datasetUnavailable`, but both call sites pass it from inside the `:` else-branch of a ternary that already tested `datasetUnavailable` — `app/investment/[area]/page.tsx:274` vs `:474`, and `app/investment/page.tsx:101` vs `:260` (also gated by `topDevelopments.count > 0`, which is 0 on an outage). The prop is always `false` where it is read. Only the new test exercises it.

### Low — inconsistent handling of a missing export (CONFIRMED)
`app/investment/page.tsx:52-54` excludes `export_missing` from `datasetUnavailable`; `app/investment/[area]/page.tsx:183` and `app/print/investment/[area]/page.tsx:146` include it. Same missing file → "run the exporter" on one page, "dataset unavailable" on another.

### Low — `report_pdf_downloaded` double-fires on the skip path (CONFIRMED)
`components/report/ReportModals.tsx:243` fires it after `runDownload()`, and `runDownload` → `onDownload` → `app/report/page.tsx:4172` fires it again. Pre-existing, but the PR's claim is precision about this event.

### Low — retrying from the gate error state re-posts the lead (CONFIRMED)
`ReportModals.tsx:206-231`: `handleSubmit` guards only `status === "saving"`, so "Try Again" after a PDF failure re-POSTs `/api/inquiries` and re-fires `inquiry_submitted`.

### Low — the comparison spinner the PR claims to fix never rendered (CONFIRMED)
`app/report/page.tsx:5592`: `compareGeoResult && !compareGeoResult` is statically false. The pre-PR compare failure was silence, not an endless spinner — and there is still no loading state during comparison generation.

### Low — geocoder nits (CONFIRMED)
`app/api/geocode/route.ts:56-70` retries a 5xx immediately with no backoff and never drains the body; `:392` still serves a genuine 404 with 30-day `CDN_HEADERS`. `httpStatusFromFetchError` (`components/report/report-generation-failure.ts:104-108`) recovers status by regexing an English error string — acknowledged in-file, but it is the only thing standing between an outage and blame-the-reader copy. No length cap on the `address` param before it is forwarded upstream.

## Claims vs. diff
- "retry re-arms each path's own gate — proven by a test asserting a real second POST": true for **instant only**. The corridor test (`report-generation-failure-live.test.tsx:172-187`) asserts the card renders and never clicks retry; shared-report and comparison retries have no test at all — which is why the two dead buttons shipped.
- "Geocode failures now classify: 503/timeout → …": the route does; the client does not, whenever `cachedFetch` has a prior success for that address (High #2).
- "…renders a dataset-unavailable state on /investment, /investment/[area], /print, **and MajorDevelopments**": the MajorDevelopments state cannot render (Medium #4).
- Error-boundary tests assert existence, copy, and that the button calls `reset`; none renders a throwing child inside the boundary, so "the boundary actually catches" rests on Next's file convention alone. Acceptable, but the claim "12 tests" overstates the coverage depth.
- PDF/email promise safety, TIF/socrata/community-investment typed results, and the both-halves + control-case test pattern are delivered as described.

## Scope creep
Minor only. `lib/zoning-point-lookup.ts` gains a diagnostic-only message change unrelated to the four findings. `components/report/FundingWindowChart.tsx` now value-imports `EMAIL_REPORT_TIMEOUT_MS`/`isTimeoutError` from `ReportModals`, coupling a chart to the modal module; those constants belong in a shared module.

`app/api/support-request/route.ts:109-114` and `app/api/email-report/route.ts:249-252`. A failed Chamber alert produces `console.error` and nothing else: `createReportLead` (`lib/report-email-delivery.ts:126`) has no notified/notification-status column, and no retry or queue exists. The PR premise ("never a silent broken promise") is delivered at the visitor and not at the Chamber. Fix: persist notification status on the lead row and add a staff view/alert for `notified = false`.

**2. CONFIRMED — the `/api/email-report` half of the diff has zero consumers; the response fields are unreadable dead code.**
`app/api/email-report/route.ts:254-262` returns `helpDelivered` / `helpContact`, but `ReportEmailResponse` (`lib/report-email.ts:23-27`) declares only `success | error | dryRun`, and its only exported sender `deliverReportByEmail` (`lib/report-email.ts:98`) has **no callers anywhere in the repo**. **3. CONFIRMED — an unconfigured/misconfigured env turns a normal success into a scary failure for 100% of opt-ins.**
`app/api/support-request/route.ts:95-115` conflates three states into one `notified: false`: send failed, `RESEND_API_KEY` unset, `INCENTIVE_HELP_INBOX` unset. Before this PR the UI ignored all three. Now, on any preview deployment or a prod env-var rotation, every visitor who ticks the support box is blocked on first click and told "our alert to the Chamber team did not go through." (Prod was verified configured 2026-08-23 per `docs/email-gate-parity.md:240`, so this is preview/regression exposure, not a live break.) Fix: distinguish `notified: "unconfigured"` from `notified: false`, or only surface the loud path when the inbox is configured (i.e. only when `contact` exists).

**4. PLAUSIBLE — the failure copy sits next to the promise it contradicts, at the smallest type size in the dialog.**
`components/report/ReportEmailGate.tsx:690-703`. The paragraph "A real person from the Southeast Chicago Chamber of Commerce will follow up within 48 hours" is unconditional, so the visitor reads it and the "did not go through" error simultaneously; the error renders at `text-[10px]`. Fix: suppress or rewrite the 48-hour line when `supportStatus === "error"`, and raise the error's prominence.

**5. PLAUSIBLE — "direct-email path" is plain text, not a link.**
`ReportEmailGate.tsx:370`. The address is interpolated into a `<p>`; there is no `mailto:` anchor, so on mobile it is not tappable and cannot be copied by tap. No PII leak (nothing user-supplied enters a URL), and the address comes from `INCENTIVE_HELP_INBOX` env (`lib/env.ts:131`), not hardcoded. Fix: render a `mailto:` link with a prefilled subject.

**6. NIT — unauthenticated address disclosure during an outage.** `route.ts:125-130` returns `INCENTIVE_HELP_INBOX` to any anonymous caller whenever the send fails; the route has no rate limit. It is a staff intake inbox that already appears as `replyTo`-adjacent, so impact is scraping-grade only. The honeypot branch (`route.ts:66-68`) correctly returns early *without* `contact`.

**7. NIT — honeypot response now produces a false statement.** A bot tripping the honeypot gets `notified: false` and the gate renders "Your request was saved" — nothing was saved. Cosmetic.

# Review — PR #251 "R3: fork stabilization"

**Verdict: NEEDS-FOLLOWUP** — no user-facing regression found (all 4 changed suites pass locally; CI run 33503967329 green), but the headline "ratchet" is trivially defeatable and two PR-description claims are not delivered by the diff.

## Findings (severity order)

1. **The ratchet can be driven to 0 by a cosmetic change that removes no duplication.** CONFIRMED.
   `lib/source-guard/fork-similarity-ratchet.ts:51` (`MIN_BLOCK_LINES = 8`). Measured: injecting `{/* cosmetic */}` every 7th line into `components/report/ReportDisplay.tsx` takes the metric from **1383 lines / 30 blocks → 0 lines / 0 blocks**. The paired test then instructs the contributor to "Set FORK_DUPLICATION_BASELINE to 0", permanently retiring the guard. Any run-splitting edit (comment injection, a variable rename, a reflow) lowers the number without unifying anything. Fix: measure with a token/AST-shingle metric that survives interleaved noise, or require the *lowering* commit to also cite the shared module it extracted; at minimum assert `blocks.length` and `largest` alongside the total so a collapse to 0 is itself a failure.
2. **The ratchet is exact-equality, not a ratchet — the PR text says otherwise.** CONFIRMED.
   `lib/__tests__/fork-similarity-ratchet.test.ts:53` — `if (report.duplicatedLineCount !== FORK_DUPLICATION_BASELINE) throw`. PR body: "CI fails if the count ever EXCEEDS the committed baseline." It fails in **both** directions. Failure scenario: an unrelated PR edits three lines inside one of the 30 duplicated blocks, duplication drops to 1380, CI goes red on a change that improved things, and the author must edit an unrelated test file to land. Fix: `if (actual > baseline) throw`, and warn (not fail) on a decrease — or keep the strictness but say so in the docs.
3. **"Closing the audit's exact blind spot" is only partly closed — a fourth hand-built action row is still unguarded.** CONFIRMED.
   The sweep is `readdirSync(components/report)`, non-recursive, `.tsx` only (`lib/source-guard/fork-parity.ts:68,398`). `components/map/MapPolygonPanel.tsx:2623,2632,2641,2787` still hand-builds "Save Report" / "Email This to Me" / "Download PDF" outside the shared component — in a file this same PR edited. `components/workspace/SaveReportModal.tsx:72,133` likewise. Fix: sweep by content (all `app/**` + `components/**` `.tsx`) rather than by one directory, or add MapPolygonPanel to the fork-file list.
4. **Item 4's stated bug is unreachable on the code path it "fixes".** CONFIRMED.
   The drawn-area dispatch consumes the **un-lensed** report: `components/report/ReportDisplay.tsx:569` and `app/report/page.tsx:4310` both pass `report={report}` (the `normalizePublicReportForDisplay` result), never `lensed` (`ReportDisplay.tsx:238-241`). Persona title overrides are applied only inside `applyPersonaLens` (`lib/report-personas.ts:733`) and only to bucketed sections, none of which are the eight drawn-area titles. The new test fakes the rename by hand rather than calling `applyPersonaLens`, so it cannot catch this. The change is harmless/defensive, but "persona-lens title renames can't silently drop sections" describes a bug that was not occurring here.
5. **The new state-order derivation is allow-list based, so the silent-desync class is not actually eliminated.** CONFIRMED (latent).
   `app/report/__tests__/report-page-live-renderer.test.tsx:405` lists exactly one expandable hook; `lib/source-guard/react-state-order.ts:101` only counts `useState` it can see. Scenario: someone adds a second stateful custom hook to `ReportDisplay` — the runtime counter sees its slots, the derivation does not, the hand-maintained array does not, and the new "matches exactly" test stays **green** while every later slot is seeded wrong. Today only `useVacancySpreadsheetSection` is called, so nothing is broken yet. Fix: fail when a call site invokes any `use[A-Z]*` identifier declared in-repo that is not in the expand list.
6. **The workstation row's Save/Email copy is now policy-derived where it was hardcoded.** PLAUSIBLE (low).
   `components/report/VacancySpreadsheetSection.tsx:1013` → `ReportActionButtons` → `getReportActionPolicy` (`lib/report-action-policy.ts:31`). A drawn-area report whose `reportType` is neither `dev-feasibility` nor `best-location` and whose title lacks "vacancy" would now render "Save to Workspace" / "Email Report" instead of "Save Report" / "Email This to Me". Unreachable via `MapPolygonPanel.tsx:787` (emits `best-location`), so no live regression; the new test fixture also uses `best-location`, so the branch is untested. The spreadsheet row is safe by construction (`lib/vacancy-spreadsheet-scope.ts:61` gates community-area scope on `isVacancyReport`).
7. **Analytics parity test compares event NAMES only.** PLAUSIBLE (nit). `lib/__tests__/report-analytics-parity.test.ts` scans `trackEvent("literal")` inside each fork's `ReportDisplay`. Payload metadata still diverges — `capital_partner_clicked` carries `originSource` on the workspace fork (`ReportDisplay.tsx:469`) and not on `page.tsx:4053` — the same drift class the PR set out to end. Also `cleanMetadata` (`lib/analytics-events.ts:326`) truncates to 25 keys and the shared envelope now contributes 5 base keys instead of 2, so the *caller's* fields are the ones dropped first on any wide event.
8. **No events lost, no PII newly exposed.** CONFIRMED-clean. Diffed name sets against `711098f`: `page.tsx` unchanged (15), workspace fork +3 (`report_pdf_downloaded`, `share_link_copied`, `program_link_clicked`), `VacancySpreadsheetSection` unchanged. No double-fire (support items are excluded from `trackSectionLinkClick` by `!isSupportNetworkItem`; the drawn-area branch early-returns so only one row mounts). Sink is first-party `/api/events`; new `zipCode` is derived from an `address` already sent. Nothing moved server-side.
9. **Action-row consolidation is behavior-preserving.** CONFIRMED-clean. Both rows keep button order (download → save → packet → email → share), the share gate is the identical predicate, `shareLabel`/`downloadSlot` reproduce the old copy, no aria attribute or link target existed to lose. Only diff: the shared button adds `cursor-pointer` the workstation row lacked.

## Claims vs. diff
- "CI fails if the count ever EXCEEDS the committed baseline" — false; it fails on any change (finding 2).
- "the ratchet … the debt can only shrink" — the *number* can be shrunk to zero without shrinking the debt (finding 1).
- "closing the audit's exact blind spot" — one of the remaining rows (`MapPolygonPanel`) is still outside every guard (finding 3).
- "persona-lens title renames can't silently drop sections" — that path never received lensed titles (finding 4).
- "removes the whole silent-failure class" — removes today's instance, not the class (finding 5).
- Test counts disagree with themselves: PR body says 5,950 passed, the merge commit says 5,943.

## Scope creep
Title promises three things; the PR also lands (4) eight new `SECTION_IDS` + a new exported `sectionMatchesIdOrTitle` in `lib/report-engine.ts`, edits to `components/map/MapPolygonPanel.tsx`, and (5) a wholly new 188-line `lib/source-guard/react-state-order.ts` harness. Items 4 and 5 are independently reviewable and share no dependency with 1–3; they should have been separate PRs. `lib/pdf-report.ts` is touched only to delete a now-shared helper (fine).
