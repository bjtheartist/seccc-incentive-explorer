## Track 1 — Structure & Data Model

This section specifies the information architecture, schema additions, readiness model, portability flow, and legacy-surface disposition for the packet. Everything here layers onto the code that already exists (commit `a8f5add`): `lib/incentive-preparation.ts` (canonical model — `BusinessProfileInput`/`Snapshot`, `PreparationTask`, `calculatePreparationTimeline`), the packet API (`app/api/incentive-preparation/route.ts`, `[id]/route.ts`, `[id]/support-request/route.ts`), the two workspace pages, and `scripts/migrate-incentive-preparation.ts`. The simpler duplicate type file `components/incentive-preparation/types.ts` is **not** canonical and is reconciled against `lib/incentive-preparation.ts` (Section 1.6).

The boundary doctrine (locked 2026-05-21, `docs/audit-2026-05-21-summary-and-plan.md` lines 169-220) governs every decision below: the packet organizes and prepares, it never determines eligibility, certifies, tracks compliance deadlines as obligations, or submits. Every eligibility-shaped output is phrased as a self-check the applicant performs, dated, and re-verifiable — never a determination the tool issues.

---

### 1.1 Information architecture: two parts on four categories

The brief requires foundational-first structure, then incentive-specific overlays. The code already has the right primitive: `PreparationTaskCategory = "foundation" | "goal" | "dependency" | "certification"` (`lib/incentive-preparation.ts`). We do **not** add categories. Instead we introduce a **`phase`** axis orthogonal to `category`, so the same task list renders as two parts and drives two timelines (Section 1.3).

```
PreparationTaskPhase = "foundation" | "incentive"
```

**Part 1 — Foundation (phase: `foundation`).** Everything obtainable and reusable *before* a target incentive is chosen. Maps to the matrix Sections 1A/1B/1C. Sub-grouped in the UI by the matrix's three headings, all carrying `category: "foundation"`:

- **General information** (matrix 1A) — identity the business always knows: legal name, DBA, entity type, formation date, EIN, addresses, contact, business description, NAICS, employee counts, IL SOS file number, City license number + status.
- **Background & context** (matrix 1B) — qualifying facts assembled once: structured ownership, voluntary owner demographics, 3-year revenue history, net worth/liquid assets, startup/chain/other-locations flags, ineligible-use self-screen, property record, prior-incentive history, community-impact narrative, compliance self-checks.
- **Continuity documents** (matrix 1C) — artifacts obtained once and reused, each expiry-governed: site-control proof, W-9, EIN doc, IL Certificate of Good Standing, 3-yr tax returns, income/bank statements, business plan + projections, COI, org/ownership chart, 6-year AV/EAV analysis, pro forma.

**Part 2 — Incentive-specific (phase: `incentive`).** Layered on top only after a target program is chosen. Maps to matrix Section 2. Uses the categories already generated by `buildPreparationTasks`:
- `category: "goal"` — goal-overlay answers (the 7 existing overlays) plus program-specific fields (matrix 2A-2D deltas: SBIF applicant-type/tier, NOF corridor/Sources-and-Uses, County class/PIN basis, cross-program prerequisite flags).
- `category: "dependency"` — program-required docs and verification steps with external owners (`landlord`/`accountant`/`program_administrator`/`local_partner`), e.g. two contractor bids, EDS, IDOR clearance, consent ordinance.
- `category: "certification"` — the always-last `OFFICIAL_CERTIFICATION_TASK_ID`, unchanged, `applicantOnly: true`.

**Implementation.** Add a `phase` field to `PreparationTask` in `lib/incentive-preparation.ts`. Populate it in `buildPreparationTasks`: the three `FOUNDATION_*` tasks plus every new foundation task (Section 1.2) get `phase: "foundation"`; all goal-overlay, program-requirement, doc, verification, financials/tax, site-control/zoning/local-support, advisor-review, and certification tasks get `phase: "incentive"`. This is a purely additive field; `normalizePreparationTasks` continues to sort certification last within its phase.

Ordering within the flat list is preserved exactly as today (`buildPreparationTasks` push order: identity → address → contact → goal → program-requirements → docs → verification → financials → conditional site/zoning/support → advisor → certification), so foundation-first is already true in sequence; `phase` just makes it a first-class, renderable boundary the API and UI can split on.

### 1.2 BusinessProfile schema additions

The current snapshot has 15 fields (`lib/incentive-preparation.ts` lines 69-85) and cannot honestly support "80-90% ready" (matrix Section 4). We extend `BusinessProfileInput`, `BusinessProfileSnapshot`, and the `business_profiles` table. Three rules govern the additions:

1. **Every new field carries provenance.** `fieldProvenance` already exists and is "the right mechanism to extend" (matrix Section 4). Each new field gets a provenance entry: `{ source, enteredAt, asOf, expiresAt?, note? }`. This is what drives the staleness display and the readiness count.
2. **Recurring documents become typed with expiry metadata**, not buried in the untyped `licenses` JSON. `licenses` stays only as an escape hatch for genuinely program-specific overflow.
3. **Structural (repeatable/multi-row) data becomes sub-records**, not free text or single scalars.

**New scalar fields (add to `BusinessProfileInput`/`Snapshot` and as columns in `scripts/migrate-incentive-preparation.ts`):**

| Field | Type | Matrix ref | Note |
|---|---|---|---|
| `ein` | `string \| null` | 4.1 (highest priority) | Blocks W-9, EDS, IDOR, all county/state filings |
| `businessLicenseNumber` | `string \| null` | 4.2 | Promoted out of `licenses` JSON |
| `businessLicenseStatus` | `"active" \| "expired" \| "unknown" \| null` | 4.2 | Standing flag |
| `ilSosFileNumber` | `string \| null` | 4.3 | Good-standing pull + SOS confirmation |
| `businessDescription` | `string \| null` | 4.4 | Narrative, distinct from `industry` bucket |
| `netWorth` | `number \| null` | 4.6 | SBIF landlord gate |
| `liquidAssets` | `number \| null` | 4.6 | SBIF landlord gate |
| `startupFlag` | `boolean \| null` | 4.7 | Derived from `formationDate`, stored because forms ask it literally |
| `isNationalChainOrFranchise` | `boolean \| null` | 4.7 | SBIF disqualifier |

**Employee-count granularity (matrix 4.10).** Replace the single `employeeCount: number` with a typed object; keep `employeeCount` as a computed convenience total for backward compatibility in existing reads:
```ts
employment?: {
  fullTimeCurrent?: number | null;
  partTimeCurrent?: number | null;
  fullTimeProjected?: number | null;
  partTimeProjected?: number | null;
  constructionJobsProjected?: number | null;
} | null;
```

**Structural sub-records (JSON-typed columns, each row provenance-tagged):**

- `owners: OwnerRecord[]` (matrix 4.8) — replaces free-text `ownershipNotes` as the driver of SBIF's ≥7.5% branch, EDS >7.5% disclosers, and NOF's ownership chart. `ownershipNotes` is retained only as a supplemental free-text field.
  ```ts
  interface OwnerRecord {
    name: string;
    address?: string | null;
    ownershipPct?: number | null;
    role: "owner" | "gp" | "lp" | "beneficiary" | "developer" | "occupant";
    isControllingEntity?: boolean | null;
    demographics?: OwnerDemographics | null; // voluntary, consent-flagged (matrix 4.9)
  }
  interface OwnerDemographics {
    consentGiven: boolean;   // required true to store; framed voluntary / no effect on outcome
    raceEthnicity?: string | null;
    gender?: string | null;
    lgbtqia?: boolean | null;
    veteran?: boolean | null;
    familyOwned?: boolean | null;
  }
  ```
  Demographics are stored only when `consentGiven === true`, with UI copy stating they are voluntary and do not affect any outcome (mirrors the consent gate already enforced on support-requests in `[id]/support-request/route.ts`).

- `annualGrossSales: RevenueYear[]` (matrix 4.5) — 3 discrete years, not one number; drives SBIF eligibility and the 90/60/30% tier.
  ```ts
  interface RevenueYear { year: number; amount: number | null; isProjection?: boolean; }
  ```

- `otherLocations: BusinessLocation[]` (matrix 4.7) — `{ address, activity }[]`.

- `complianceSelfChecks` (matrix 4.12) — each a self-reported status + date, never a determination:
  ```ts
  complianceSelfChecks?: {
    cityDebtStatus?: SelfCheck | null;
    childSupportComplianceStatus?: SelfCheck | null;
    scofflawSelfCheck?: SelfCheck | null;
    ineligibleUseScreen?: SelfCheck | null;   // matrix 1B ineligible-use self-screen
  };
  // SelfCheck = { result: "clear" | "issue_found" | "not_checked"; asOf: string | null; note?: string }
  ```
  Boundary framing: labels read "Self-reported — verify with the administering agency before relying on it," never "cleared" or "eligible."

**Typed continuity documents (matrix 1C + 4.13).** Add a typed `documents` array replacing ad-hoc `licenses` usage for the recurring items, each with an expiry class (Section 1.2.1):
```ts
interface ContinuityDocument {
  kind: "site_control" | "w9" | "ein_doc" | "good_standing" | "tax_returns"
      | "financial_statements" | "business_plan" | "insurance_coi"
      | "org_chart" | "av_eav_analysis" | "pro_forma" | "community_impact_narrative";
  present: boolean;
  obtainedAt?: string | null;
  expiresAt?: string | null;      // computed from staleness class where applicable
  leaseEndDate?: string | null;   // site_control only
  note?: string | null;
}
```

**Property record (new one-to-many entity, matrix 4.11).** SBIF/NOF/County rules attach to the *property*, not the applicant, so a business has many properties. New `business_properties` table (migration authored alongside `scripts/migrate-incentive-preparation.ts`), FK `business_profile_id`, columns:
```
pin (text[]), township, ward, tifDistrictOrCorridor,
eligibilityAreaDetermination (text), eligibilityDeterminationCheckedAt (timestamp),
siteControlBasis ("own" | "lease" | "purchase"), leaseEndDate,
propertyTaxStanding ("current" | "delinquent" | "unknown"), propertyTaxStandingAsOf,
priorIncentiveHistory (jsonb: [{ program, amount, date }])  // per-property, for SBIF cooldown/offset
```
`eligibilityAreaDetermination` stores the *result of the applicant's locator check* plus the date checked — the binary geographic gate as a dated self-check, consistent with the boundary (we surface the determination the applicant found on the official map; we do not issue it).

#### 1.2.1 Expiry / staleness handling

Encode matrix Section 3 as a pure function in `lib/incentive-preparation.ts`, e.g. `documentStaleness(item, asOf): "fresh" | "soft_stale" | "hard_stale" | "not_applicable"`. Rules the function implements:

- **Soft-fresh** (IL Certificate of Good Standing): no statutory expiry, flag `>90 days` as soft-stale, re-pull is minutes.
- **Rolling** (3-yr tax returns / income / bank statements): most-recent-3-years window; stale when newest year < currentYear − 1.
- **Annual** (COI): stale past `renewalDate`.
- **Event-based** (lease site-control): stale past `leaseEndDate`; NOF needs ≥5-yr remaining term.
- **Recency gate** (property-tax standing, compliance self-checks): stale past a configurable window (default 90 days) — must be re-verified at each program gate.
- **Hard-gate items are explicitly NOT bankable** (IDOR Tax Clearance ITR-1, EDS, City Debt Check, SSN submission, 50%-financing proof, triennial affidavit). Per matrix Section 3 and the "NOT core" list, these are **never** stored as foundation documents and never counted toward readiness — they are generated as `phase: "incentive"`, `category: "dependency"`/`certification` tasks with owners `program_administrator`/`accountant`/`applicant`. Banking them as "done" would be dishonest about readiness and is the explicit reason the brief caps the claim at 80-90%, not 100%.

Staleness is surfaced, never auto-mutated: an expired item flips its foundation task back to `needs_document`/`needs_owner_answer` in the *live* profile view. This is also why the immutable snapshot must change (Section 1.4).

### 1.3 Readiness model — honest "80-90% ready"

The brief's "80-90%" is a *structural* claim about how much foundational work is reusably done, not a probability of approval. We compute and display it as a plain fraction, never a score or a likelihood.

**Definition.** For a given profile (optionally in the context of a chosen program):

```
foundationReadiness = {
  totalCore: number,      // count of applicable core items (fields + docs) for this business
  currentCore: number,    // core items present AND not hard-stale
  staleCore: number,      // present but soft/hard-stale (need refresh)
  missingCore: number     // absent
}
```

- `totalCore` is computed from the matrix core list, filtered by applicability (e.g. `netWorth`/`liquidAssets` count only when a property with `siteControlBasis: "own"` or a landlord applicant-type is in play; demographics never count toward the denominator since they are voluntary).
- An item is **current** only if present *and* `documentStaleness !== "hard_stale"` (soft-stale still counts as present-but-flagged, shown in `staleCore`).
- Add `calculateFoundationReadiness(profile, asOf)` to `lib/incentive-preparation.ts`, returning the object above. It reads provenance/expiry, so it is the single source of truth for both the number and the per-item badges.

**Display (honest phrasing).** Render as "**N of M foundational items current**" with the stale/missing counts broken out — e.g. "18 of 21 foundational items current · 2 need a refresh · 1 not started." The percentage, if shown at all, is `currentCore / totalCore` labeled "**Foundation prepared**," immediately followed by the standing verification line: *"This measures how much reusable groundwork is done. It is not an eligibility decision or an approval estimate. Program administrators make final determinations."* (reuses the locked boundary copy pattern from `app/programs/page.tsx` ~line 508).

**Per-program readiness.** When a program is chosen, show a *second* fraction over the incentive-phase tasks: "K of J program items prepared," with the hard-gated items (IDOR, EDS, bids, financing, certification) explicitly listed as "obtained at application time — not part of the reusable foundation." This is the honest mechanism that keeps the headline at ~80-90%: the reusable foundation is near-complete, the last mile is intentionally program-gated.

**No new packet status enum values.** `summarizePreparationStatus` and `PreparationPacketStatus` (`foundation_complete` … `ready_to_submit`) stay as-is; readiness is a computed overlay, not a status. `foundation_complete` now has a precise meaning: `missingCore === 0 && staleCore === 0` for the applicable core set with no program chosen yet.

### 1.4 Two timelines

The clearest gap (all three readers, matrix Section 4): `calculatePreparationTimeline()` computes exactly **one** combined critical path over the interleaved graph, surfaced as a single "Preparation timeline" section (`app/workspace/incentive-preparation/[id]/page.tsx` lines 295-299). The brief requires two.

**Change `calculatePreparationTimeline` to compute per-phase timelines.** Signature becomes `calculatePreparationTimeline(tasks, asOf)` returning:
```ts
interface PreparationTimelines {
  foundation: PreparationTimeline;   // over tasks where phase === "foundation"
  incentive: PreparationTimeline | null; // over phase === "incentive"; null until a program is chosen
  combined: PreparationTimeline;     // retained for back-compat / overall view
}
```
The existing critical-path / parallelizable-levels / `earliestRealisticDate` algorithm runs unchanged, just three times over three task subsets. Because incentive-phase tasks `dependsOn` foundation tasks, the incentive timeline's `earliestRealisticDate` is computed with foundation tasks treated as prerequisites (their remaining weeks feed the incentive critical path only where a real `dependsOn` edge exists), so the two timelines compose honestly rather than double-counting.

**API.** `packetTimeline()` in `app/api/incentive-preparation/[id]/route.ts` returns `timelines` (the object above) instead of a single `timeline`. `timeline_json` stored on the packet holds the full object.

**UI.** `[id]/page.tsx` renders two sections:
1. **"Foundation timeline — completing your base profile"** (always shown): range, earliest-realistic date, critical path over foundation tasks.
2. **"Application timeline — [Program name]"** (shown once a program is chosen): range from today (or from foundation-complete) to earliest realistic application-ready date, with program dependency/certification tasks on the critical path.

Both keep the existing labels (Preparation range / Earliest realistic date / Critical path), pluralized into two headed blocks. Boundary copy under the application timeline: *"Dates are planning estimates based on typical processing times, not commitments by any agency. Windows and deadlines are set by the administering program."*

### 1.5 Foundation-only packets + portability

Two brief requirements are currently blocked by the same constraint: `POST /api/incentive-preparation` validates **both** `goalType` and `programName` as required (`app/api/incentive-preparation/route.ts`), so there is no foundation-first path and no cheap second application.

**Make program/goal optional at creation.** Relax the validation: a packet may be created with a profile and **no** `goalType`/`programName`. Such a packet is a **foundation packet** — `buildPreparationTasks` runs the foundation branch only (identity/address/contact + the new foundation tasks), produces only the foundation timeline, and reports `foundation_complete`/`needs_information` status. Program selection is layered on later ("a couple of program-specific fields," per the brief) rather than forced upfront.

**One profile, many packets — the persistent entity.** The business profile is the durable object; packets are program-specific views layered on it. `business_profiles` already lists per user; we make the profile the hub:
- `GET /api/business-profiles/[id]` returns the profile plus `foundationReadiness` and a list of its packets.
- A new **`POST /api/incentive-preparation` with `{ profileId, goalType, programId, programName }` and no `profile` body** attaches an existing profile to a new program packet in one call (the API already inserts a new `business_profiles` row *only when no `profileId` is given*, so this path exists — we expose it from the UI).

**The one-to-two-click flow** ("qualifying program found in a report" → "program-specific packet started, everything prefilled"):

1. In a report, `StartPreparationPacketButton` (`components/incentive-preparation/StartPreparationPacketButton.tsx`) already stashes a `PreparationContext` (address, projectGoal, industry, up to 4 program candidates) into sessionStorage. **Extend the button** so, when the user has an existing profile, clicking it routes to `POST /api/incentive-preparation` with `{ profileId: <their most-complete profile>, goalType, programId, programName }` derived from the report context — **click 1** creates the program packet with the entire foundation prefilled from the persistent profile.
2. The new-packet page is bypassed when a profile + program candidate are both known; it is shown only to (a) first-time users with no profile, or (b) users who must choose among multiple profiles or multiple candidate programs. In that case the page is reduced to exactly the residual questions.

**The "couple of remaining questions"** are precisely the `needs_owner_answer` goal-overlay fields plus the program's own delta fields (matrix 2A-2D) that are *not* in the core profile — e.g. for SBIF: applicant-type single-select, reimbursement-tier self-placement, project budget table; for NOF: corridor type, Sources-and-Uses, requested grant amount. Everything in matrix 1A/1B/1C is carried from the profile and never re-asked. To make second applications cheap, **persist goal-overlay answers on the packet** (`goalAnswers_json`) and, when a new packet is created from the same profile with the same `goalType`, prefill those answers — so a second application against the same goal is genuinely one or two clicks plus program-specific fields.

**"Start another application from this profile" affordance.** Add a button on both the packet-detail page and the profile view that calls the attach-existing-profile path above with a newly chosen program — closing the portability gap all three readers flagged (today reuse requires manually returning to `/new` and re-selecting).

#### 1.5.1 Snapshot immutability must change

Today `profile_snapshot_json` is frozen at creation by a DB trigger (`trg_incentive_packet_profile_snapshot_immutable`, `scripts/migrate-incentive-preparation.ts`), so editing the live profile never updates an in-flight packet's foundation completion — directly breaking the "continuity of effort, one persistent profile" promise (all three readers). Resolution:

- The **live `business_profiles` row is the source of truth** for foundation readiness and foundation-task status. Foundation tasks are computed against the live profile, not the frozen snapshot.
- `profile_snapshot_json` is **retained but redefined** as a point-in-time *audit record* of what the profile looked like when a program packet was created (useful for the handoff artifact — "these are the facts as of the day you started this application"). Keep the immutability trigger for that audit copy.
- Add a `profile_id` FK column and a "**Refresh foundation from profile**" action that recomputes the packet's foundation tasks/timeline from the current live profile on demand (and automatically on packet load), so an edited profile propagates without violating the audit snapshot's immutability. This preserves both properties: an honest live foundation state *and* an immutable record of the application-time facts the applicant will certify.

### 1.7 Replace save-the-report; keep watch-areas/digest

The workspace page (`app/workspace/page.tsx`, 553 lines) renders four stacked sections — Packets, Projects, Watched Areas, Recent Reports — with competing CTAs (header "Generate Report" → legacy `/report?source=workspace`; section "Start a packet"). Disposition:

**KEEP untouched (orthogonal to packets, PR #47):** `WatchedArea` (`lib/user-intel.ts`, `lib/types/user-intel.ts`), the weekly deadline digest (`lib/watchlist-digest.ts`, `app/api/cron/watchlist-digest/route.ts`, `app/api/watchlist/route.ts`). These are area-level monitoring, have no packet equivalent, and share no code with incentive-preparation. The Watched Areas section stays exactly as-is.

**ABSORB → the profile/packet model:**
- `business_projects` (legacy static checklist) is functionally superseded by `PreparationTask` (richer categories, owners, dependency graph, timeline). Its live dependency is only `GoalType`/`GOAL_OPTIONS` imported by `lib/incentive-preparation.ts` line 1 — that enum stays in `lib/workspace.ts` (not dead code). The projects *surface* is absorbed: the projects page's one live affordance is already "Start Preparation Packet" (`app/workspace/projects/[id]/page.tsx`), carrying `goalType/address/industry` forward. We keep that seed path during transition.
- `saved_reports` (the "save-the-report" snapshot the brief says packets replace) is absorbed: a saved report becomes a *seed* for a packet (the nullable `saved_report_id` FK already exists), not a persistent object of its own. Once a packet exists for that report moment, the saved-report row is a vestigial duplicate.

**RETIRE (staged, not deleted day one):**
- Update workspace framing first: change the page eyebrow ("Business Workspace") and h1 ("Your incentive projects") — stale legacy framing (matrix/readers) — to center the profile + packets. Point the header CTA at packet/profile creation, not `/report?source=workspace`.
- Add a deprecation affordance on the Projects and Recent Reports sections ("This has moved into your business profile") with a one-click "bring into a packet" action, rather than three permanent competing lists.
- Retire the standalone Projects/Reports CRUD surfaces once migration (below) is verified and analytics show packet adoption. Do not drop the tables or their APIs in the same change that ships the schema additions — retirement is a later, separate PR.

#### 1.7.1 Migration note for existing saved reports

A backfill script (new, authored alongside `scripts/migrate-incentive-preparation.ts`) is required; it is inherently **lossy** and must be run on a disposable Neon branch and verified before prod (per Billy's DB rule):

- **`saved_reports` → seed profiles:** `report_data_json`/`wizard_state_json` can populate `physicalAddress` and `industry` where present. Most core fields (`legalName`, `ein`, `contactEmail`, `entityType`, `annualGrossSales`, ownership, property PINs) are **not captured** in a saved report and must be re-collected — so migration creates a *draft profile with provenance `source: "migrated_saved_report"`* and marks unmapped fields missing (they correctly count against readiness). Do not fabricate values.
- **`business_projects` → seed profiles + foundation tasks:** carry `goalType`, `address`, `lat/lon`, `industry`, `budgetRange`. Legacy checklist `completed` booleans have **no clean mapping** to `PreparationTaskStatus` (different granularity); do not auto-mark foundation tasks complete from them — surface them as a note on the migrated profile so the user reconfirms. This keeps the readiness number honest rather than importing unverified "done" state.
- **FK decision:** retain `saved_reports.project_id` for historical linkage during the transition; drop only when Projects is retired.
- **Watchlist/digest data:** untouched — nothing migrates.
- **Terminal state for the migration loop:** every legacy `saved_reports`/`business_projects` row for a user is either (a) linked to a seed profile or (b) explicitly marked "kept as legacy read-only." Report the counts; if the only remaining rows are intentionally-legacy, stop.
